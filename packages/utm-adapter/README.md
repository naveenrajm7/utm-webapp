# UTM adapter

`UtmPort` is the boundary for VM inventory, detail, console target discovery, capability detection, clone, configuration, power control, deletion, and guest execution. Inject `UtmAdapter` into the API or supply a fake `UtmPort` in tests. The adapter launches processes with argument arrays and no shell, validates VM UUIDs and guest arguments, and applies time and output limits. Failures have a stable `UtmError.code` and `operation`.

The adapter uses UTM's fixed scripting interface for structured inventory, VM detail, console discovery, and stopped-only name/RAM/CPU configuration. It uses `utmctl clone <UUID> --name <name>` and `utmctl delete <UUID>`. `getSerialDevice(id)` resolves a configured PTY only for a started VM. `getVncTarget(id)` accepts only a configured loopback QEMU `-vnc` argument and also requires a started VM. Serial and display capability flags describe configuration and remain true while stopped. Apple displays are not advertised as VNC displays.

Clone, configure, and delete capability flags are true only for stopped QEMU VMs on installed UTM 5.0.6 with working `utmctl`, the combination validated below. The host flags indicate that this path is available; per-VM flags also check backend and state. Unknown versions, Apple and unavailable backends, and the unvalidated JXA clone/delete fallback return `unsupported`. A running or transitioning VM returns `conflict` before capability evaluation. Guest execution and `networkPresets` remain disabled. Configuration accepts only `name`, `memoryMiB`, and `cpuCores`: supplying `networkInterfaces` to UTM replaces the complete NIC list. The existing stop method is a force stop through both `utmctl stop <UUID> --force` and JXA's default stop. The adapter reconciles new clone UUIDs and deleted UUIDs against inventory and reads back edits. Callers must enforce deletion confirmation and ownership policy; this port has no ownership database.

## Direct VM management validation (2026-10-11)

- Installed UTM version: `utmctl version` returned `5.0.6`; `utmctl help clone` showed `clone <identifier> [--name <name>]`; `utmctl help delete` showed `delete <identifier>` with no confirmation.
- The named disposable source `vagrant_test_default_1744595654130_77151` (`10EC4AB2-91F6-42AB-A3DF-0996C75B80CF`) was stopped and QEMU before cloning. `utmctl clone 10EC4AB2-91F6-42AB-A3DF-0996C75B80CF --name 'Codex phase2 adapter disposable 2026-10-11'` created `127380F6-5685-444C-BBCE-F15251F51F1E`. JXA `configure` changed only that clone's name, RAM from 4096 to 3584 MiB, and cores from 0 to 2. Detail readback showed the same `emulated` NIC. `utmctl delete 127380F6-5685-444C-BBCE-F15251F51F1E` removed that UUID; inventory still showed the stopped source with its original settings.
- The compiled `UtmAdapter` then independently cloned the same stopped source to `F1AD2A68-AB58-4858-BC9F-C694CA4ABDBF`, changed only that clone to 3072 MiB and 1 core with a new name, read the values back, and deleted it. Final source readback remained stopped at 4096 MiB and 0 cores. Adapter capability flags for the source were clone/configure/delete true, guestExec false, and networkPresets empty.
- Remaining gates: Apple backend clone/configure/delete, another UTM version, JXA clone/delete when `utmctl` is absent, and concurrent external mutations were not tested live. Keep their flags false. To validate another backend/version, use a newly named disposable stopped source of that exact backend/version, clone it, edit only the clone, verify name/RAM/CPU and NIC preservation by readback, delete only the clone, and confirm the source is unchanged. A timeout outcome also needs inventory inspection before any retry.

## Earlier read-only and console verification (2026-10-10)

- Installed UTM 5.0.6 scripting dictionary exposes VM configuration, PTY serial ports, and both QEMU and Apple serial configurations.
- Adapter `getCapabilities`, `listVms`, and `getVm` succeeded in the Mac GUI session. Inventory contained 30 stopped VMs. Detail calls succeeded for all 30, including QEMU and Apple backends. One stopped QEMU VM had a configured loopback VNC argument; configured PTY serial ports were also observed. These are configuration observations, not proof of a working live transport.
- The restricted sandbox could not reach the UTM app (`Application can't be found`); the same read-only calls passed with the Mac GUI-session permission.
- At that time no named disposable VM was supplied. Live `getSerialDevice`, `getVncTarget`, and guest execution were not checked in that read-only pass. Their validation is separate from the direct management checks above.

At this phase, `npm run build --workspace=@repo/utm-adapter`, `npm run lint --workspace=@repo/utm-adapter`, and `npm run test --workspace=@repo/utm-adapter` passed. Jest ran 19 fake/process tests.
